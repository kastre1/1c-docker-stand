## 🎯 Зачем нужна графика

Наш 1С-сервер работает **headless** (без графики) — это правильно для сервера. Но **некоторые операции** требуют **GUI**:

1. **Активация Community-лицензии** — только через диалоговое окно 1С
2. **Создание информационной базы** — мастер создания ИБ
3. **Загрузка конфигурации** — через Конфигуратор
4. **Отладка** — иногда нужно «посмотреть глазами»

**Проблема:** контейнер `1c-server` находится на Ubuntu VM (Linux), а **пользователь работает на Windows**. Как показать окно 1С из контейнера на Windows-экране?

**Решение:** **X11 forwarding** — Linux-приложения рисуют окна на удалённом X-сервере.

---

## 🖼️ Что такое X11 (короткая справка)

**X Window System (X11)** — оконная система, используемая в Linux/Unix. Её архитектура **клиент-серверная**:

- **X-сервер** — то, что **рисует окна** (на вашем экране)
- **X-клиент** — приложение, которое **хочет нарисовать окно** (например, 1С)

**Ключевая идея:** X-клиент и X-сервер **могут быть на разных машинах**, соединённые по сети.

```
Linux (где работает 1С)          Windows (где пользователь)
┌─────────────────────┐          ┌─────────────────────┐
│  X-клиент (1С)      │          │  X-сервер (VcXsrv)  │
│  "хочу нарисовать   │          │  "рисую окно на     │
│   окно"             │          │   экране Windows"   │
└──────────┬──────────┘          └─────────┬───────────┘
           │                                │
           └──────── X11 Protocol ──────────┘
                    (TCP :6000)
```

**Что нужно:**
1. Запустить **X-сервер на Windows** (VcXsrv)
2. Настроить **Linux-приложение** на отправку графики в X-сервер через переменную `DISPLAY`

---

## 🖥️ Шаг 1. Установка VcXsrv на Windows

**VcXsrv** — бесплатный X-сервер для Windows.

### 1.1. Скачать

Скачайте с [https://sourceforge.net/projects/vcxsrv/](https://sourceforge.net/projects/vcxsrv/) и установите.

### 1.2. Настроить XLaunch

**XLaunch** — графический мастер настройки VcXsrv.

1. **Пуск → XLaunch**
2. **Display settings:**
   - **Multiple windows** (или One large window)
   - Display number: **0**
3. **Client startup:** **Start no client**
4. **Extra settings:**
   - ✅ **Clipboard**
   - ✅ **Primary Selection**
   - ✅ **Disable access control** ← **ОБЯЗАТЕЛЬНО!**
   - ❌ Native opengl
5. **Finish**

**Что делает «Disable access control»:** разрешает подключения к X-серверу **по TCP** без авторизации. Без этой галочки X-сервер принимает только локальные Unix-сокеты, и Docker-контейнер не сможет к нему подключиться.

### 1.3. Проверить, что VcXsrv слушает TCP

**В PowerShell на Windows:**

```powershell
netstat -an | findstr ":6000"
```

**Ожидаемо:**
```
TCP    0.0.0.0:6000    0.0.0.0:0    LISTENING
```

Если пусто — VcXsrv не слушает TCP. Перезапустите XLaunch с «Disable access control».

### 1.4. VcXsrv должен быть запущен постоянно

Иконка VcXsrv должна быть в системном трее. Если закрыть — графика перестанет работать.

## 🧪 Шаг 2. Проверка X11 с хоста Ubuntu

Прежде чем пробрасывать X11 в Docker, убедимся, что **X11 работает с самой Ubuntu VM**.

### 2.1. Установить X11-утилиты на Ubuntu

```bash
sudo apt install -y x11-apps xauth
```

### 2.2. Установить DISPLAY и запустить тест

```bash
export DISPLAY=192.168.0.129:0.0
xhost +192.168.0.173
xeyes
```

**Разбор:**
- **`DISPLAY=192.168.0.129:0.0`** — куда слать графику:
  - `192.168.0.129` — IP Windows-хоста
  - `:0` — номер дисплея (как в XLaunch)
  - `.0` — номер экрана
- **`xhost +192.168.0.173`** — разрешаем X-серверу принимать подключения от Ubuntu VM
- **`xeyes`** — тестовое X-приложение («глаза», следящие за курсором)

**Ожидаемо:** на Windows появится окно с глазами.

⚠️ Если появится ошибка `xhost: must be on local machine to add or remove hosts` — значит, `DISPLAY` установлен **не туда** или X-сервер не принимает TCP.

⚠️ Если `xeyes` не появляется — проверьте:
- VcXsrv запущен, иконка в трее
- `netstat -an | findstr ":6000"` показывает LISTENING
- В XLaunch была галочка «Disable access control»

## 🐳 Шаг 3. Проброс X11 в Docker-контейнер

### 3.1. Зачем нужен TCP, а не Unix-сокет

**Два способа пробросить X11 в Docker:**

| Способ | Как | Когда работает |
|---|---|---|
| **Unix-сокет** | Монтировать `/tmp/.X11-unix` | Только если X-сервер **на хосте** (Linux) |
| **TCP** | `DISPLAY=IP:0` | Работает **всегда**, включая Windows-хосты |

**Наш случай:** X-сервер на **Windows**, а контейнер — на **Ubuntu VM**. Unix-сокет **не подходит**, только **TCP**.

**Почему MobaXterm не подошёл:**
- MobaXterm создаёт X11-туннель **внутри SSH-сессии**
- Туннель живёт **только пока активна SSH-сессия**
- Docker-контейнер **не имеет доступа** к этому туннелю
- **Решение:** использовать VcXsrv напрямую с TCP

### 3.2. Разрешить X-серверу принимать подключения

На Ubuntu VM:

```bash
xhost +192.168.0.173
```

**Ожидаемо:** `192.168.0.173 being added to access control list`.

### 3.3. Запустить GUI-контейнер

```bash
cd ~/projects/1c-server
docker compose run --rm \
  -e DISPLAY=192.168.0.129:0.0 \
  -v 1c-server_1c_data:/home/usr1cv8 \
  1c-server bash
```

**Разбор команды:**

| Параметр | Что делает |
|---|---|
| **`docker compose run --rm`** | Запускает **новый** контейнер (не тот, что `up -d`), удаляет его после выхода |
| **`-e DISPLAY=192.168.0.129:0.0`** | Передаёт переменную `DISPLAY` внутрь контейнера |
| **`-v 1c-server_1c_data:/home/usr1cv8`** | **Критично:** монтирует **тот же volume**, что у основного контейнера, чтобы данные сохранялись |
| **`1c-server`** | Имя сервиса |
| **`bash`** | Команда внутри (вместо `ragent`) |

⚠️ **Важно:** `-v 1c-server_1c_data:/home/usr1cv8` — **обязательно**. Без этого всё, что создаст GUI-клиент (включая `.lic` и конфиги), пропадёт при выходе.

⚠️ **`--network` указывать не нужно** — `docker compose run` автоматически подключает контейнер к сети `1c-net`, где уже есть `pg-1c` и `1c-server`.

### 3.4. Проверить, что DISPLAY и сеть работают

Внутри GUI-контейнера:

```bash
echo $DISPLAY
# Ожидаемо: 192.168.0.129:0.0

getent hosts pg-1c
getent hosts 1c-server
# Ожидаемо: IP-адреса в Docker-сети (172.x.x.x)

(echo > /dev/tcp/1c-server/1540) 2>/dev/null && echo "1c-server:1540 OPEN" || echo "CLOSED"
(echo > /dev/tcp/pg-1c/5432) 2>/dev/null && echo "pg-1c:5432 OPEN" || echo "CLOSED"
# Ожидаемо: оба OPEN
```

### 3.5. Запустить GUI-клиент 1С

```bash
export GDK_BACKEND=x11
export LIBGL_ALWAYS_INDIRECT=1
/opt/1cv8/x86_64/8.3.26.1540/1cv8s -DisableHWA
```

**Разбор:**

| Параметр | Что делает |
|---|---|
| **`GDK_BACKEND=x11`** | Указывает GTK использовать X11, а не Wayland |
| **`LIBGL_ALWAYS_INDIRECT=1`** | Отключает прямой рендеринг OpenGL (через TCP не работает) |
| **`1cv8s`** | **Server** — серверная версия клиента (даёт полный мастер) |
| **`-DisableHWA`** | **Отключает аппаратное ускорение** — критично для X11 через TCP |

**Почему `1cv8s`, а не `1cv8`:**
- `1cv8` — обычный толстый клиент, мастер создания ИБ идёт по «пользовательскому» пути
- `1cv8s` — **серверная версия**, даёт **полный мастер** с опцией «Создать новую ИБ без конфигурации»

**Почему `-DisableHWA`:**
- Без этого флага 1С пытается использовать GPU
- X11 через TCP **не поддерживает GPU-рендеринг**
- Результат: окно **не появляется** (платформа падает молча)
- С флагом — рисует в software-режиме, всё работает

**Ожидаемо:** на Windows откроется окно «Запуск 1С:Предприятия».

## ⚠️ Типичные ошибки

### Ошибка 1. `Unable to initialize GTK+ or connect to the windowing system`

**Причина:** `DISPLAY` установлен неправильно, или X-сервер не принимает TCP.

**Решение:**
1. Проверить `echo $DISPLAY` внутри контейнера — должно быть `192.168.0.129:0.0`
2. Проверить на Windows `netstat -an | findstr ":6000"` — должно быть LISTENING
3. Проверить, что в XLaunch была галочка **«Disable access control»**

### Ошибка 2. `/bin/sh: 1: /sbin/ip: not found`

**Причина:** в образе `1c-server` нет пакета `iproute2`.

**Решение:** добавить `iproute2` в `Dockerfile` (см. [раздел 04](04-containers.md)).

**Проверка:**
```bash
docker exec -it 1c-server ls -la /sbin/ip
```

### Ошибка 3. `Хранилище сертификатов Linux не обнаружено`

**Причина:** не установлены сертификаты Минцифры.

**Решение:** добавить в `Dockerfile` скачивание сертификатов (см. [раздел 04](04-containers.md)).

**Проверка:**
```bash
docker exec -it 1c-server bash -c "ls -la /usr/local/share/ca-certificates/"
docker exec -it 1c-server bash -c "grep -c 'BEGIN CERTIFICATE' /etc/ssl/certs/ca-certificates.crt"
```

### Ошибка 4. Окно 1С открывается, но пустое

**Причина:** 1С пытается отрисовать окно за пределами видимой области.

**Решение:** проверить координаты окна:
```bash
xwininfo -root -tree | grep -i 1c
```

### Ошибка 5. Графика работает, но `xeyes` тоже не запускается

**Причина:** X-сервер не запущен или не принимает TCP.

**Решение:**
1. Проверить иконку VcXsrv в трее Windows
2. Перезапустить XLaunch с «Disable access control»
3. Проверить `netstat` на Windows

## 💡 Полезные приёмы

### Приём 1. Автоматизировать запуск

Вместо каждый раз писать длинную команду — сделать alias на Ubuntu VM:

```bash
echo "alias 1c-gui='docker compose run --rm -e DISPLAY=192.168.0.129:0.0 -v 1c-server_1c_data:/home/usr1cv8 1c-server bash'" >> ~/.bashrc
source ~/.bashrc
```

Теперь:
```bash
cd ~/projects/1c-server
1c-gui
```

### Приём 2. Не закрывать GUI-контейнер

Если планируешь работать с GUI долго — **не выходи** из контейнера после `exit`. Все данные сохраняются в volume, но **сам процесс контейнера** удобнее держать живым.

### Приём 3. Проверка X11 без 1С

Прежде чем запускать 1С, всегда проверяй X11 простыми `xeyes` или `xclock`. Если они работают — X11 настроен. Тогда ошибка с 1С будет в чём-то другом.
